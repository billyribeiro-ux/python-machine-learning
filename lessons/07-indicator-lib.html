Module 7 · Indicators

Build a Better Indicator Library

The payoff module. We unify NumPy, TA-Lib, pandas-ta, and Numba indicators behind one registry so any indicator is addressable by name with settings. That single abstraction is what powers config-driven features, parameter sweeps (Module 9), and Optuna optimization (Module 13).

1. Why a registry beats fifty call sites

As your codebase grows, indicators get called from features, scanners, backtests, and dashboards. If each call site hard-codes talib.RSI(...) or s.rolling(20).mean(), then changing an indicator, sweeping its parameters, or letting an optimizer choose it means editing code everywhere. The fix is to make an indicator data: a (name, settings) pair that a registry resolves to a function. Now a config file, a grid, or an Optuna trial can request indicators it has never heard of.

🎯 The core idea

combine(ohlcv, [("rsi", {"window": 14}), ("zscore", {"window": 20})]) → a feature frame. The list of specs is the configuration. Code consumes indicators it doesn't know the names of at write-time. That inversion is the whole design.

2. The registry, in full

The implementation (quantlab/indicators/registry.py) is deliberately tiny: a dict from name to a function f(ohlcv, **params) → DataFrame, a @register decorator, and combine(). Each built-in wraps our from-scratch NumPy indicators and returns a settings-named column (e.g. rsi_14) so combined frames are self-documenting.

3. Runnable: combine indicators & extend the library

Expected output

Registered indicators: ['atr', 'ewma', 'ret', 'rsi', 'sma', 'std', 'zscore'] Combined columns: ['sma_20', 'sma_50', 'rsi_14', 'zscore_20', 'atr_14', 'ret_5'] Custom indicator registered: True

4. Multi-backend dispatch (the design that scales)

The registry's real power is that a registered indicator can be backed by any engine. The same "rsi" name could resolve to our NumPy version for a single series, a Polars .over("symbol") version for a whole universe (Module 3), or a Numba version for path-dependent ones (Module 8). Callers never know or care which computed the column — they just ask for "rsi".

🔬 Settings as a typed object

For strategies (not just single indicators) we go one step further and use a dataclass for settings — see quantlab.strategies.ComboParams. A dataclass is hashable, loggable, diffable, and serializable, so a parameter set becomes a first-class value you can store in an Optuna trial or a results table. Loose **kwargs can't do that. This is the difference between "it works" and "it scales to 10,000 experiments."

🧱 Why this is "a better library"

It's open for extension (one decorator adds an indicator), uniform (every indicator has the same call shape and warmup discipline), composable (combine blends any mix), and backend-agnostic (NumPy/Polars/TA-Lib/Numba behind one name). Off-the-shelf libraries give you functions; this gives you a system that the rest of QuantLab — features, sweeps, optimization, the dashboard — is built on.

🛠️ Try it

Register a "donchian" indicator returning the rolling high and low channel (two columns), then add it to a combine spec alongside rsi and atr. Confirm available() now lists it and the combined frame has all the columns. You've extended a production indicator library in under ten lines.
