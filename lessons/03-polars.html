Polars for Speed & Scale

When "5,000 symbols × 10 years of minute bars" no longer fits pandas' patience or your RAM, Polars takes over: a multi-threaded, Arrow-backed DataFrame with a lazy query optimizer. The mental shift is from imperative (do this, then that) to expressions (declare what each column is; let the engine plan it).

1. Why Polars exists

pandas is brilliant and single-threaded. Its operations often materialize intermediate copies, and it predates Apache Arrow. Polars is built on Arrow's columnar memory, runs across all your CPU cores, and — in lazy mode — looks at your entire query before executing, so it can reorder filters, drop unused columns (projection pushdown), and avoid materializing intermediates.

2. Expressions: the core idea

A Polars expression (pl.col("close")...) is a recipe for a column, not the column itself. You hand a list of recipes to select / with_columns and Polars runs them in parallel. This is why there's no per-row Python and no index gymnastics — you describe columns, the engine does the work.

🔬 when/then/otherwise > apply

Anytime you reach for .apply(lambda ...) you've dropped back into slow Python. Polars' when().then().otherwise() expresses branching as data, so it stays vectorized and parallel. Most "I need a loop" moments in indicator code are actually a when/then in disguise.

3. Per-symbol windows in ONE pass (the killer feature)

Remember the Module 2 rule: on a stacked panel you must group before any rolling op. Polars makes this a first-class, parallel operation with .over("symbol") — a window expression that computes per group without breaking the frame apart. One expression, every symbol, all cores.

🧱 Why this beats the pandas version

The pandas equivalent needs groupby(...).transform(lambda ...) for each feature, each one a Python-level callback per group. Polars' .over("symbol") is a native windowed expression: no Python callback, parallel across groups, and the optimizer fuses the whole with_columns into one pass over the data. On a real universe this is the difference between seconds and minutes.

4. Lazy mode: let the optimizer earn its keep

Eager Polars runs each step immediately (great for exploration). Lazy Polars (pl.scan_parquet / .lazy()) builds a query plan and only executes on .collect() — after optimizing it. It will read only the columns and rows you actually use, even from files larger than RAM. This is how the warehouse in Module 4 stays fast at scale.

🔬 Read the plan, trust the plan

.explain() prints the optimized query plan. You'll see the symbol == "AAPL" filter and the column selection pushed down into the parquet scan, so Polars never reads MSFT's rows or the columns you didn't ask for. Engineers who read the plan catch accidental full scans before they cost an hour.

6. Interop: use the right tool per step

You don't have to pick a side. Convert with pl.from_pandas(df) and pldf.to_pandas() — both are cheap because they share Arrow buffers where possible. A common, pragmatic pattern: heavy multi-symbol munging in Polars, then hand a single tidy frame to scikit-learn (which expects pandas/NumPy).

🛠️ Try it

Add a .over("symbol") RSI to m3_multisymbol.py. Polars has no built-in RSI, so build it from primitives: the gain/loss split with when/then, then ewm_mean(alpha=1/14) per symbol (Wilder smoothing), then the 100 - 100/(1+rs) formula. Compare the last value to quantlab.indicators.rsi on the same symbol — they should match. You'll have built a multi-symbol RSI that runs on all cores.
