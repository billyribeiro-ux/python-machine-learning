DuckDB: Your Market-Data Warehouse

A scanner over thousands of symbols needs data that's organized, fast to query, and bigger than RAM. DuckDB is an in-process analytical SQL engine that reads parquet directly — no server, no import step. We use it to turn a folder of parquet files into a queryable market-data lake on your laptop.

1. "SQLite for analytics" — and why that's perfect here

DuckDB runs inside your Python process (like SQLite), but it's column-oriented and vectorized for analytical queries (aggregations, window functions, joins over millions of rows). Crucially, it queries parquet and even pandas/Polars DataFrames in place — the files are the database. No ETL, no copying gigabytes into a server.

🔬 Why SQL, when you know pandas/Polars?

Three reasons a principal engineer keeps SQL in the toolkit: (1) it scales to larger-than-RAM parquet by streaming; (2) window functions over partitions express per-symbol rolling logic declaratively and run in C++; (3) the same query works on 1 symbol or 10,000, and is portable to a real warehouse later. SQL is the lingua franca your data infrastructure will eventually speak.

2. Parquet: the storage format that makes this fast

Parquet is columnar, compressed, and self-describing. Storing OHLCV as parquet (instead of CSV) means a query for just close reads only the close column off disk, and a query for one symbol reads only that symbol's file. We partition by timeframe and symbol so DuckDB can prune entire files it doesn't need.

3. Window functions: per-symbol indicators in SQL

SQL window functions are the database world's answer to Polars' .over(): OVER (PARTITION BY symbol ORDER BY timestamp ROWS BETWEEN n PRECEDING AND CURRENT ROW) computes a rolling statistic per symbol, in time order, looking only backward (no leak). The same query computes a 20-day SMA for every symbol at once.

🔬 QUALIFY and named WINDOW clauses

Two touches that mark fluent SQL: a named WINDOW w20 AS (...) defines the frame once and reuses it (DRY, and the optimizer computes it once); QUALIFY filters on a window function's result (here: keep only the latest row per symbol) without a subquery. DuckDB supports both. Clean SQL is as much an engineering signal as clean Python.

4. Joins: combine price with anything

The real power of SQL is relating datasets: prices to a sector map, signals to fundamentals, your fills to a benchmark. Here we join each symbol's bars to the market (SPY) to compute a simple relative-strength line — outperformers float to the top of a scanner.

🧱 The warehouse pattern, in your pocket

MarketDataLake (in quantlab/data/cache.py) gives you the architecture real quant platforms use — partitioned columnar storage queried by a vectorized SQL engine — shrunk to a laptop and fed by the same provider-agnostic data layer. A nightly lake.ingest(...) keeps it fresh; everything downstream (scanners in Module 14, ML features in Module 11) reads from it. You built a data platform, not just a script.

⚠️ Timestamps, types, and partitions

Two things to watch: store timestamp as a real timestamp type (not a string) so ORDER BY and date functions work; and keep partition cardinality sane — one parquet file per symbol per timeframe is great, one tiny file per day per symbol creates thousands of files and slows scans. Our lake partitions by timeframe then symbol, which is the sweet spot for symbol-oriented queries.

🛠️ Try it

Add a query to m4_windows_sql.py that returns, for each symbol, the count of days where the 20-day z-score exceeded +2 (an overbought tally) over the last year. Hint: compute the z-score in a CTE, then WHERE timestamp >= current_date - INTERVAL 1 YEAR and GROUP BY symbol. You've just written the core of a cross-sectional scanner in pure SQL.
